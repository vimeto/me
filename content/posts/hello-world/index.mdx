## The GPTQ flipping range

Round-to-nearest quantization on a scalar weight $w$ (in grid units) flips to a
different level when an additive perturbation pushes $w$ across the nearest
half-integer boundary. If the perturbation is approximately Gaussian with std
$\sigma$,

$$
p_\text{flip}(w) = 2 \left(1 - \Phi\!\left(\frac{d(w)}{\sigma}\right)\right),
$$

where $d(w)$ is the distance from $w$ to the nearest half-integer. The
"flipping range" is the set of $w$ where $p_\text{flip}(w) \ge \tau$.

## What runs under the hood

- **MDX** compiled by `@mdx-js/rollup` and loaded through `import.meta.glob`.
- **Frontmatter** validated at import time by a strict Zod schema.
- **Block props** are also Zod-validated at render time (`src/schemas/blocks.ts`).
- **Compute registry** at `src/components/mdx/compute/index.ts` maps string keys
  to pure functions — adding a new visualization only requires a new entry.

```ts
export const computeRegistry: Record<string, ComputeFn> = {
  'gptq.flippingRange': gptqFlippingRange,
}
```

<Callout tone="aside" title="Why a registry">
  Keeping compute logic out of JSX lets the MDX stay declarative and
  statically validatable. The same `ParamPlot` block powers every future
  post — only the `compute` key and `params` change.
</Callout>
